# 07 运维清单：环境、进程、金丝雀

长批量（几十个求解任务连跑）死于环境的概率不亚于死于物理。本文是运维 SOP。

## 1. 僵尸进程清理（每次排错后必做）

PyFluent 会话退出不干净是常态。强杀脚本/驱动后，残留会吃掉许可证会话和内存，
症状是：**新会话启动超时（TimeoutError）、gRPC 连接被重置（WSAGetOverlappedResult
10054）、甚至导入报"文件格式不支持"的假错**。

```powershell
taskkill /F /IM fluent.exe
taskkill /F /IM cx2520.exe      # Fluent 的 cortex 服务端，一人多个
taskkill /F /IM Discovery.exe
```

清完必须验证：
1. 许可证端口在听：`netstat -ano | findstr :1055`；
2. **金丝雀测试**（见 §3）。

## 2. 许可证

- 许可证服务挂了（lmgrd/ansyslmd 抢端口、多实例打架）时：全杀 →
  用 `lmgrd.exe -c <license文件> -l <日志>` 手动起单个实例 → lmstat 查端口。
- 一个求解占一个求解会话许可；驱动里**串行**跑构型（别并行抢座）。

## 3. 金丝雀测试（环境手术后的体检）

任何"杀进程/改环境"操作之后，别直接投批量——先跑 2 分钟的金丝雀：

1. 启动一个 meshing 会话；
2. 导入一份**已知良好**的旧几何（历史上成功过的文件）；
3. 导入成功 → 环境健康，可以开工；失败 → 继续排环境，别怀疑新文件。

这一条在实战里把"新文件坏了"和"环境坏了"两种假设 2 分钟内分开，
避免了对着一堆完全正常的文件排查一晚上。

## 4. 驱动设计模式

```python
for cfg in CONFIGS:
    if os.path.exists(summary(cfg)): continue      # 断点续跑
    rc = subprocess.call([PY, solve_one, ...],      # 子进程隔离
                         stdout=logfile(cfg), env={...})
```

- **子进程隔离**：单个构型崩溃只丢自己，驱动继续；每构型独立日志文件；
- **summary 文件 = 完成标记**：删目录即强制重跑；
- **顺序串行**：许可证和内存都不宽裕，并行得不偿失；
- 驱动自身挂了，正在跑的子进程可能陪葬——重跑即可，已完成构型不受影响。

## 5. Windows + Git Bash 杂项

- `python` 可能指向 WindowsApps 的假 python——**用 conda 环境的绝对路径**。
- shell 工作目录会在命令间重置——**一律绝对路径**。
- 后台任务用 `run_in_background` 或 `(... &)`；命令链里 `rm` 失败会中断 `&&` 链。
- 被锁的旧日志文件（trn）删不掉就绕开，别恋战。

## 6. 自校验哲学（本文最重要的一节）

管线每一层都要有一个**物理上必然成立的断言**，它比任何"看起来对"都可靠：

| 层 | 断言 | 实战战果 |
|---|---|---|
| 几何 | 布尔后实体数、刚体变换体积不变 | 抓过静默丢零件 |
| 网格 | 负体积=0、OQ 进日志、阶梯化计数 | 预告过求解发散 |
| 求解 | 入口速度读回、每步耗时档位、力爆炸早停 | 抓过假收敛 |
| 数据 | 驻点压力为正、对称分量≈0、窗口面积==已知面积 | 抓过节点映射错位 |
| 量纲 | 自积分 vs 原生报告对账 | 抓过 Cm/N 量纲陷阱 |

这些断言全都不需要懂 CFD 就能写，但每一个都在实战里省过几小时的排错。
**新管线上线前，先写断言，再写功能。**

## 7. 排错的一般顺序（血泪总结）

1. 先看**症状是否物理可能**（负驻压、零力、超光速耗时）→ 不可能 = 数据链路错，不是物理错；
2. 症状复现于"已知良好输入"吗？→ 复现 = 环境问题；不复现 = 新输入问题；
3. 一层一往下走，每层用该层的断言定位；
4. 修完做金丝雀，再投批量。
